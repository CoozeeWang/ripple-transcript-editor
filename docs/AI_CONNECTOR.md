# MCP connection

Ripple's personal local MCP connection lets external AI read a precisely selected manuscript version in the currently open project, including a manuscript that is not open in the editor. AI discusses editing rules and the save mode: a new version or an explicit update to the selected editable version. Originals remain read-only. Background saves do not switch the open editor; edits to the active version retain normal editing and comparison behavior.

The current connection uses personal ChatGPT tunnels or local Claude/WorkBuddy clients, without a public Ripple server. See [local AI connections](LOCAL_AI_CONNECTIONS.md). The former public pairing service is retained only as development history.

## First-time connection

1. Add **Ripple** in your AI application. Follow its authorization link.
2. In Ripple open **Settings → AI-assisted editing → Connect Ripple** and select **Show pairing code**.
3. Enter that code on the Ripple authorization page opened by the AI application, check the requested access, and authorize. The code expires after 10 minutes and works once only.
4. Select Ripple in the AI application's conversation. The desktop connection becomes enabled after pairing succeeds.

Enable MCP connection explicitly; this preference is remembered across restarts. Turning it off stops the window connection and retains saved setup. Per-client deletion removes only that client’s local configuration and credentials. Requests can access manuscripts in the current project, using its existing folder authorization; they do not expose arbitrary filesystem paths, other projects, trash or audio. Requested text leaves the computer through the selected AI client. Start with a synthetic project.

Older internal testing builds used the official OpenAI tunnel and manually configured credentials. Those fields are not part of the new user flow. Existing test connections do not automatically migrate to a new service; adding the deployed Ripple connection and authorizing it is necessary. The already configured ChatGPT test plugin should be retained until public deployment and compatibility testing are complete.

## Editing and analysis

For independent imports, only the manuscript designated as the original appears as a read-only original. Internal import snapshots remain stored for source/timing recovery; they are excluded from version menus and MCP comparison candidates. They are not a second user version or evidence of human editing preferences. Existing transcription-engine originals remain available for compatibility.

Ask in ChatGPT: “I've edited part of v1. Look at my corrections and continue from this paragraph.” Specify the start paragraph or a precise position. If the start is missing or ambiguous, ChatGPT must ask. For a task without an exact version, AI must list candidates and ask the user before starting; it cannot choose the newest, active or sole version by default. `list_project_interviews` returns paginated interview/recording/version names and IDs without manuscript text or paths. `read_project_interview` requires the selected interview, recording and exact version IDs to create a snapshot; missing version selection only returns candidates. Use that snapshot with the existing editing and marks tools. AI reports the actual target names and IDs, and each snapshot/task remains bound to its own target. `read_current_interview` remains available for explicitly requested current-document work. `read_editing_examples` lists comparison candidates with `segment_ids: []`; it automatically selects a baseline only when the sole other version is an original. Otherwise ChatGPT must list the candidates and ask which to use, then pass its `comparison_version_id`. IDs such as `m1:e1` distinguish versions within the current interview even when names repeat. Results identify `before_version` and `after_version` by name and ID. Samples contain the actual selected versions' text and include full recorded merge/split groups. Missing files or unreliable lineage return reasons instead of guessed differences; identical selected samples do not establish that the whole manuscript is unchanged. Differences may include previous AI changes, so confirm which changes are human-authored before learning personal preferences.

Once the rules, scope and save choice are agreed, long continuation uses durable incremental tasks. Read one short batch, submit changed text plus checked unchanged IDs, and save that batch directly to the agreed manuscript. Reuse the next batch returned with the save result. New-version mode creates only one work version, then all later batches update that version. Atomic mode remains available for up to 48 segments. Task rules are retained only in that task’s journal; saving a batch or completing a task does not turn them into future interview preferences. Unchanged words retain their original timing, replacements inherit their source range, and inserted words have approximate timing through the same algorithms used for manual editing.

ChatGPT normally gives short explanations and a completion summary. Full differences belong in Ripple; it should reproduce full text or a complete changes list only when requested. For analysis, it should cite relevant snippets and timestamps, distinguish evidence from interpretation, and state when it has read only part of the interview. Analysis does not edit the manuscript.

## Recovery and limits

- Changing the source, selecting another version/interview, or closing the interview invalidates an old read snapshot. Read again for analysis. Durable continuation retains its agreed scope; reopen its target and re-read an affected batch when the user requests recovery.
- Incremental tasks and pending proposals are stored locally in the current recording’s transcript container. The editor shows saved progress, pause/resume/end controls and pending proposal previews. After reopening, `list_project_continuations` finds tasks and their exact targets in the current project without opening those manuscripts. `list_continuations` retains the current-document view. Use the saved task ID to resume its original target. Returning to a task never authorizes another project or automatically starts an AI service. Legacy atomic tasks still remain transient and are lost when their connection/controller is replaced. Retry a completed task through its status/result instead of starting another task.
- Repeated publication of a task returns the same result. A timeout means the outcome may be unknown: inspect task status and the Ripple version list before starting another operation.
- Name conflicts use a new suggested name, never overwrite. If a conflict arises after preparation, refresh the current source and prepare again. Atomic tasks with no text changes create no version. Incremental new-version mode creates its one work version at the first checked batch, even if that batch is unchanged.
- The connector edits text and supports explicitly scoped deletion and adjacent same-speaker merges; it does not change speakers or split paragraphs. It accepts up to 32 paragraphs per staging call, paginates text reads, and rejects individual paragraphs longer than 12,000 UTF-16 code units for editing; split those in Ripple first. Read pagination supports longer paragraphs without splitting grapheme clusters.
- Only one enabled Ripple window may answer. Turn off other connected windows if the current interview is ambiguous.
- Platform tool permission prompts are separate from conversational style agreement. A matching confirmation summary records the agreed plan; it does not authenticate a human chat message.

## Developer entry point

The bundled Python interpreter exposes `python -m app.connector_mcp --credential-file /path/to/app-data/connector/client.key`, with optional `--url http://127.0.0.1:18701`. The MCP adapter reads only its credential file and calls the local authenticated bridge. It never takes project paths. Window and client keys have different roles.

For source runs, set `RIPPLE_DATA_DIR` to an absolute directory outside the repository. The desktop backend generates owner-only connector credentials there. The native window retrieves its role key through a Tauri command; public HTTP routes never return credentials. New builds run the outbound relay worker with protected credentials. Never enable raw HTTP logs containing manuscript text.

Automated source, browser fixtures, native builds, actual ChatGPT conversations, and installed-app acceptance are separate evidence. A successful MCP handshake is not an editing-quality or desktop acceptance result. Windows, ChatGPT desktop, and a second AI application require their own validation before compatibility is promised.

## Annotations and highlights

After upgrading Ripple with new MCP tools or changed input parameters, keep the desktop application running with its MCP connection ready. In the ChatGPT plugin management page, use **Refresh tools**, confirm the new metadata, then start a new chat with Ripple. Installing a desktop build alone does not refresh the tool list available to ChatGPT; older chats may retain the earlier capabilities. For version comparison, `read_editing_examples` must expose `comparison_version_id`; an older two-parameter definition cannot submit a user's version selection. For saving to the current version, `prepare_continuation` must also expose `save_mode`; refresh tool metadata and start a new chat after the desktop upgrade.

For separately imported versions without shared source IDs, Ripple compares only complete, ordered time windows supported by unchanged text of at least 12 characters that occurs uniquely in both manuscripts. Results disclose this alignment method; matching IDs or overlapping timestamps alone are insufficient. Missing boundaries, repeated context or ambiguous timing return an explicit reason. These comparisons still do not establish who authored a change.

Segment merges and deletions use the same continuation tools, without extra direct-write tools. Before continuation, ask whether to save a new version or update the current editable version; reuse a choice the user already made. `prepare_continuation` requires an explicit `save_mode` (`new_version` or `current_version`) before a task is created. The confirmed summary binds that choice and the source version ID. Read-only originals cannot use `current_version`. After agreement, `prepare_continuation` accepts `allowed_actions: ["edit", "merge_previous", "delete"]`; the default allows only text edits. `stage_continuation` accepts an optional `action` per change (default `edit`). For `merge_previous`, `after` contains only this segment's revised text: Ripple joins it to the nearest retained preceding segment with a paragraph break, skipping explicitly staged deletions. Both retained segments and the intervening deletions must be fully within scope; the retained neighbors must have the same speaker. `delete` requires `after: ""` and a whole segment. Include unchanged segments to complete coverage. For example, after deleting a filler between two same-speaker segments, request `merge_previous` on the later retained segment. Stage the filler deletion first or together with the merge. Deletion alone does not automatically merge neighbors; a merge cannot cross the agreed range or a remaining speaker boundary. Deleting the entire transcript is rejected. Source IDs and full `before` text are checked before accepting each batch, independent of submission order. Publication follows the agreed save mode and reports merge/delete counts. `new_version` preserves the source and opens comparison; `current_version` keeps the editable version name, ID and version count, while leaving the original and other versions intact. Current-version changes form one normal undo step during the editing session; undo history is not a permanent before/after version and is not promised after restart. Choose `new_version` for a lasting separate comparison. Repeated publication of the same task is idempotent in either mode. A failed current-version save leaves the edits in Ripple for manual saving or undo and does not report success. Merges retain both segments' annotations, highlights and timing origins. Deleted segments and their marks are absent only from the new result. Check `continuation_status` after an uncertain result before retrying.

Annotations and highlights are added to the current editable version, without creating another version or changing text, speakers, word timestamps, or existing human marks. AI-created annotations display an **AI annotation** label and support ordinary editing/deletion. The batch is undoable in Ripple. The original read-only transcript cannot receive marks.

Use `prepare_interview_marks` with explicit segment IDs or `whole_interview: true` and the user's instructions. Stage every scoped segment through `stage_interview_marks`, including empty marks for reviewed segments. Each highlight contains a verified text quotation and UTF-16 start/end offsets (end exclusive) at grapheme boundaries. After agreement, `apply_interview_marks` saves once to the current version and opens the relevant sidebar. It returns counts and a saved status, without listing the manuscript. Existing identical notes or highlight ranges are retained once.

Use `interview_marks_status` to recover uncertain outcomes. A failed save keeps applied marks in Ripple for manual saving; repeating the same task does not repeat the write. Cancel draft tasks with `cancel_interview_marks`. Changed source text or a switched version invalidates an outstanding task.


## Add a local AI client

In Settings → AI-assisted editing → MCP connection, select the AI software:

- **Add to WorkBuddy**: confirm adding Ripple. Existing configuration is backed up and other connections are retained. Open “Experts · Skills · Connectors → Connectors → Custom connectors” in WorkBuddy, find Ripple and enable it. If it is missing, restart WorkBuddy and check again. Once enabled, ask directly in a conversation; no selection from the “+” menu is needed. An invalid configuration is left untouched. Backups are saved next to the WorkBuddy configuration with a `mcp.json.ripple-backup-` prefix.
- **Add to Claude (Beta)**: Ripple generates a local MCPB and requests opening it in Claude Desktop. Confirm installation there. Windows may have no `.mcpb` file association even when Claude is installed. In that case, use **Install the Claude extension manually**: export the extension or open its folder, then in Claude choose **Settings → Extensions → Advanced settings → Install Extension…** and select `Ripple.mcpb`. This is also available when automatic opening fails. No registry change or credential editing is needed. A dispatched open request does not prove that the installer appeared or the extension was installed.
- **Open ChatGPT to add**: opens ChatGPT Plugins. Complete the existing tunnel setup first, copy the Tunnel ID, then choose “Add custom MCP server” and “Tunnel” in ChatGPT. Existing connections do not need to be added again.

Keep Ripple open with MCP enabled. Adding configuration or opening an installer does not verify a successful AI tool call. After moving the Ripple App, add it again to update local paths. These buttons are currently delivered and tested as a macOS internal build; Windows client installation remains pending native validation.

### Packaged Windows startup checks

All packaged Python entry points initialize the dependency directory as a Python site directory before importing MCP. This processes the bundled pywin32 `.pth` and DLL bootstrap; adding the directory to `PYTHONPATH` alone is insufficient. Configuration JSON from the native window uses explicit UTF-8 bytes independently of the Windows console code page. Save failures return fixed stage codes, never raw exceptions, paths or keys.

The Windows build pipeline runs `desktop/verify-mcp-runtime.py` both on staged resources and on the installed resources under a synthetic Unicode/space path. It uses the generated WorkBuddy JSON, Claude Node launcher, and ChatGPT profile's MCP command to perform `initialize`, `tools/list` and an authenticated synthetic Unicode read, twice per entry point. Windows also checks pywin32 imports. This is a packaged-adapter regression gate with a synthetic loopback server; it does not install third-party clients, connect to OpenAI's cloud, or replace actual client GUI and project read/write acceptance.

## Incremental continuation

Use `prepare_continuation` with `delivery_mode: "incremental"`, an explicit `save_mode`, full-segment scope and agreed rules/actions. `read_continuation_batch` persists up to 24 whole segments, normally bounded to 6000 text characters, plus at most two neighbouring excerpts, each bounded to 500 graphemes. Word-origin and timing arrays stay local. Context does not expand editing permission. Pass its `batch_id` to staging and saving. Changed entries retain exact `before` checks; pass `unchanged_ids` instead of echoing unchanged text.

`save_continuation_batch` can stage and save in one call with `changes` and `unchanged_ids`, then return `next_batch`, avoiding another read/stage round trip. Separate `stage_continuation` persists an unfinished proposal before manuscript publication. A full batch must be checked before saving. The scope/save-mode summary is agreed once, not once per batch. Ordinary editor undo applies per saved batch during the session; it is not a permanent historical version.

Saving compares only the batch, its speaker definitions and structural neighbours against the text the AI read, then patches the latest manuscript. Manual changes elsewhere are retained. An overlap pauses the batch and retains the user's manuscript and proposed AI text. After the user requests resumption, `resume_continuation` retains the conflicted proposal and re-reads unsaved work from the latest text. Already completed IDs are not processed again. If remaining segments have been removed, reordered or inserted within the planned span, end the task and confirm a new range rather than silently skipping or expanding it. Merges at a batch boundary require the retained preceding segment to be inside the agreed task; its latest text and marks remain protected.

A pending local journal and a receipt written with the manuscript distinguish a completed write from an uncertain response. Retrying saved batch IDs does not duplicate versions or edits. Receipts are internal and excluded from manuscript JSON exports. Cancellation stops remaining work and preserves saved batches. Progress says saved only after persistence succeeds; a failed write retains proposals and pauses rather than claiming success. Resumption across restart needs the same project and its folder permissions, with the task’s target version still present; that manuscript need not be open.

These tools reduce repeated transcript transfer and per-stage whole-document validation. Actual model processing time and the AI application's conversation limits remain external; interruption recovery does not make the external AI run independently in the background. After installing a build with this change, refresh connected tools and start a new chat so `delivery_mode`, `batch_id`, `unchanged_ids` and the four incremental tools are visible.

## Background save behavior

Background results identify the project, interview, recording and version. Current-version writes and marks save to the selected version without changing its ID or activating it. They have no active-editor undo history: choose a new version for a persistent separate before/after copy. The original and other versions remain untouched. Background marks do not open a sidebar in the unrelated editor. The open editor shows a saved-target notice; incremental progress names the background manuscript and provides scoped pause, resume, end and pending-proposal controls.

Source validation and saving run in the same recording-directory queue. Project membership, recording identity and exact version are checked again before writes; stale text or overlapping batch changes are rejected, and uncertain saves must be checked by task status. Switching projects or closing/disabling the window invalidates project access. After adding these tools, refresh ChatGPT tool metadata and start a new chat.

### Editing ownership and task feedback

A prepared editing task reserves its exact manuscript/version for its authenticated AI client. Read-only analysis and a ready connection do not reserve a manuscript. While reserved, text, annotations, highlights, speakers and mutating undo/redo are read-only; browsing, find, playback, version viewing and other manuscripts remain available. The activity bar names a background target and shows actual task stages and confirmed saved counts, including short text and marking tasks. It does not invent a percentage.

**End editing** revokes later writes from that task. If a save is already in progress, Ripple keeps that manuscript protected until its result is known, retaining any saved changes. Idle, disconnected, paused and failed tasks keep exclusive protection until the user ends the task or a confirmed completion receipt arrives. Interrupted incremental work can be explicitly resumed after its version and content guards are checked. Saved batches and conflict proposals are retained.

Task state and the local connection belong to the window, so viewing another manuscript does not discard an in-flight marking result. If an external wait expires, query the task status before repeating a write. Ordinary short tasks and marks retain their status for the current window session; only incremental journals persist across application restarts. These rules do not block file changes made outside Ripple; existing content/version conflict checks still reject stale writes.

### Exclusive task protection and status feedback

AI feedback occupies the top status position. The exact manuscript/version is read-only to humans and other AI clients while its task is running, paused, failed or disconnected. Waiting does not automatically release protection. Other manuscripts remain editable. End editing revokes future writes and dismisses the notice after any pending save settles; saved changes remain. Only confirmed save receipts produce completed counts. A completed task has a separate close control. The latest attempt for a target replaces older notices without deleting their queryable receipts. Status queries reconcile actual task results; a late invalid request cannot replace a completed result with failure.


## Task rules, preferences and safe continuation

Ordinary manuscript reads return only explicitly retained future preferences in `current_interview_rules`. Use `set_interview_rules` with a fresh target snapshot and `confirmed_for_future_tasks: true` only after the user explicitly requests retention or replacement. Passing an empty list clears these preferences. The confirmation field records conversational agreement, not authentication of a human message. New task rules must still be explicitly supplied; current user instructions take precedence and conflicts should be clarified.

Explicit preferences use `ai-interview-preferences.json`, with source, scope and update time. Legacy `ai-connector-rules.json` is preserved as unconfirmed historical data and is never automatically loaded as current instructions, overwritten or deleted by this change. Task journals remain available for recovery and explicit historical inspection. Both preference and legacy files travel with portable project copies; they do not become device credentials.

`list_continuations` and `list_project_continuations` default to unfinished task metadata. Set `include_history: true` to locate cancelled/completed tasks; lists never return full task instructions. `continuation_status` returns terminal instructions only with `include_history_details: true`, for an explicit request to inspect history, and labels them as historical. Active task rules remain available to their owning client for explicit recovery; ownership protections still apply.

Ending editing permanently cancels the task and retains saved changes. A paused task can resume after agreement; a cancelled task cannot. To continue cancelled incremental work, inspect its status, read the exact saved version and prepare a new incremental task with `previous_task_id`, fresh agreed rules and the complete remaining range (`remaining_start_id` through `remaining_end_id`). Status also reports remaining count and a bounded ID preview. The server checks the exact ordered remaining IDs, saved receipt and version; structural changes require reviewing scope rather than dropping the predecessor parameter to bypass rejection. Manual text is read fresh, not replayed from abandoned proposals. A successor is linked to its predecessor; repeated requests must inspect the existing successor instead of creating another. Completed tasks have no continuation; uncertain saves must be resolved through receipts before creating a successor.

## Diagnose tools separately from connectivity

`connection_capabilities` reports the actual MCP server tool catalogue without reading or writing a manuscript. It explicitly leaves desktop connectivity, client-visible tools and client write permission unverified. It is not an end-to-end write test. If a chat reports only read tools, rediscover `prepare_continuation` and `save_continuation_batch` in that client and compare a fresh session before reinstalling or broadening permissions. Task cancellation does not remove tools. A successful server catalogue, desktop connection indicator or read call alone does not prove that the external client loaded write tools.

New tools and schema fields require external clients to refresh their tool metadata where supported. Desktop installation alone cannot force an existing chat to refresh. Client-specific tool filtering remains a separate reproduction/acceptance item; the diagnostics do not claim to fix external platform discovery.


## Tag operations

`read_project_tags` requires exact interview, recording and version IDs. It reads a shared tree, this version’s admitted tags and flat groups, and paginated segment ID/tag-ID assignments without manuscript text or word arrays. Current/project scope changes the tree and count scope. Current counts refer to the exact version; project counts sum independently saved versions. Counts are direct explicit tag-ID hits, not descendant aggregation; parent filtering still includes descendants. Assignments always refer to the exact target version. Empty names and case-insensitive conflicts follow the same rules as Ripple.

Use `prepare_tag_changes` with explicitly authorized `allowed_actions`, current/project scope and up to 64 changes, then show its exact target and effects. It previews without saving. `apply_tag_changes` accepts the unchanged agreed summary and commits the entire batch once through Ripple’s ordinary tag transaction. New tags/groups may define a batch-local `ref`; later IDs use `ref:NAME`. The saved result maps refs to stable IDs. Up to 10,000 explicit segment/tag pairs can be changed per batch.

Supported actions are create/rename/full-path/move/explicit merge/delete-branch, admit/remove-current-branch, create/rename/dissolve/reorder flat groups, set/transfer group membership, reorder same-parent tags in a version-local view, and assign/unassign segment tags. `reorder_tags` supplies `view` (`level`, `group` or `ungrouped`), explicit `parent_id` (null for root), and the complete `tag_ids` sibling order; group view also requires `group_id`. `place_group_tag` combines group membership, shared parent and destination sibling placement in one project-scoped atomic action, using tag_id/source_group_id/group_id/parent_id/anchor_id/after/copy. Null anchor appends, null source adds; an ancestor branch anchor may be absent from group membership and never becomes a member merely for ordering. Shift-style copy retains the source membership; descendants move in the shared hierarchy but their group memberships do not move implicitly. Group order is independent for each version and group. Name sorting is display-only and never overwrites manual priorities. Shared rename/path/move/merge/delete require project scope and validate all consuming versions’ small tag metadata, without reading their manuscript bodies. A merge is never inferred from a rename collision. Parent admission includes ancestors, while segment assignment and group membership use only the explicitly selected IDs. Current-branch removal clears only this version’s subtree membership/associations, retaining shared entities and other versions. Originals reject all tag writes. No action edits body, timing or audio.

Tag tasks lock the exact version, or all open-project editing for shared scope. Active-editor writes create one normal session undo step; background local writes do not provide editor undo. A later tag transaction in another version prevents an unsafe older undo that could remove a still-used entity. Manuscript text edits remain intact during tag undo/redo. `cancel_tag_changes` cancels an uncommitted plan; an in-flight commit may finish, so query `tag_changes_status`.

The project index retains the most recent 100 tag request receipts atomically with the transaction. After timeout/reconnect query the original task ID; repeated apply never replays a saved or subsequently undone batch. An unknown/expired receipt is not proof that the write failed and is not permission to replay. Pending plans and undo history are session-only. A saved result with `view_refresh_failed` still means the disk transaction succeeded: reopen the target safely instead of resubmitting.

Refreshing the installed desktop app does not prove the AI client has refreshed its tool metadata. Verify that the client exposes the five tag tools; retain existing credentials and refresh tools using that client’s supported UI where necessary.

### Tag storage format

Project format 2 stores each saved version’s admitted collection, flat groups, display priorities and segment/tag IDs in an authoritative `tags-<filename-sha256>.json` file beside its manuscript. `tag-storage.json` marks the container. The project index remains the shared definition authority. A revision token and body fingerprint detect stale metadata; cache state is rebuildable. Missing metadata fails safely rather than resurrecting inline tags. Ordinary tag batches journal only small metadata and the project index; content/structure edits still save their actual manuscript.

Legacy projects open without migration and expose read-only tag tools until an explicit full verified backup and upgrade. The upgraded project index is rejected by the old format-1 project opener. Retain the complete backup for rollback; do not open individual upgraded internals with old software. A copied or imported version retains independent associations and priorities. Migration, structural edits and ordinary body saves have separate costs from tag-only commands.
