# Ripple 开发与仓库工作方式

这里是准备公开的产品源码仓库。只跟踪产品代码、正式测试、合成样本、构建所需文件和现行产品文档。私人研究、内部验收、真实音频、转录稿、项目、凭据和签名材料都保存在仓库外。

从可测试的 `main` 开一条围绕单一目标的功能或修复分支。开发过程中可以保留 checkpoint commit，提交信息说明当前状态。完成工作时，按功能检查暂存内容，把源码、必要测试和对应文档放在同一功能提交中；无关改动分开。不要把个人资料、缓存或构建产物提交进去。

提交前运行与改动相称的测试。前端测试、构建、lint、后端测试和 Ruff 是自动证据；浏览器检查、Mac/Windows 打包和已安装桌面版操作分别记录，不能互相替代。`main` 应保持可测试、可构建；未完成或已知损坏的工作留在功能分支。

通过审阅后合入 `main`。临时 checkpoint 没有独立价值时可以在合并前 squash；有独立功能、修复或验收价值的提交可以保留。不要为整齐而重写现有有价值的历史；不要强推 `main`。仓库远端、可见性和发布由维护者管理。

## Issue、测试版与平台验收

问题和需求以 Issue 记录当前描述与状态。每次修改仍围绕一个清楚的目标；多个已修改的 Issue 可以汇入同一批 macOS 测试版，由使用者集中验收，再对该批做一次已安装版验收。不要求每个 Issue 单独制作或安装一个包。验收记录列出本批涵盖的 Issue、实际构建、中文和英文的检查结果，并将代码检查、浏览器、测试版、安装版和使用者确认分开。

修改时考虑 macOS、Windows 和两种界面语言。当前 Windows 原生验收留待后续集中进行；Mac 测试或构建不能写成 Windows 已通过。若某个 Issue 在 Mac 验收后结案，仍需在后续平台验收记录中保留 Windows 待验项。最终双平台发布前，按实际安装版补齐两平台与两种界面语言的检查。

## 版本和测试包命名

应用版本以 `desktop/src-tauri/tauri.conf.json` 的 `version` 为准；改版时同步核对 macOS 打包脚本中的 `CFBundleShortVersionString`，避免包内外版本不一致。单个 Issue 的提交不会自动提升应用版本。每个测试包用构建提交区分，并在文件名写明版本、平台和架构：`Ripple-<版本>-<提交短号>-<平台>-<架构>.<扩展名>`，例如 `Ripple-0.1.6-a1b2c3d-macOS-arm64.zip`。包内应用仍可叫 `Ripple.app`；交付记录写明完整提交、所含 Issue、包的校验值及实测安装版位置。正式发布的版本号、标签与安装包在发布准备阶段一致核对，不把测试包当成已发布版本。

## 按任务阅读现行规则

界面布局、可见文案、按钮、菜单、状态、焦点、快捷键、播放或版本展示有变化时，先读 [Ripple Stylebook](STYLEBOOK.md) 的相关章节。交付前核对最终做法：现行规则改变或新增时更新对应条目；规则未变时无需改写。纯内部改动跳过这一步。详细文案维护见 [文案规则](i18n/AUTHORING.md)。

GSD 的项目目标、计划和阶段状态，以及人工验收材料，保存在私人工作区。公开仓库只保留适合外部开发者使用的现行产品文档。提交前检查测试数据、截图、日志和生成文本；真实用户名、路径、最近文件和私人文稿内容不能进入公开历史。
